# The Streamlit UI (`src/evalbuilder/ui/`)

`evalbuilder ui [DIR]` runs `streamlit run src/evalbuilder/ui/app.py -- --dir DIR`.
The app is a thin presentation layer: every fact it shows comes from artifacts on disk
(loaded through the naming convention) or from pure-Python helpers in
`pipeline/setup.py` and `pipeline/jobs.py`; the pipeline itself always runs as a
background job in a separate process.

```
app.py            entry point: st.navigation over page callables, sidebar showing the project,
                  page registry in session_state["pages"] for st.switch_page / st.page_link
project.py        THE project (folder or uploads) every page follows; the persistent setup form;
                  bundle loading (cached by file fingerprint); per-run bookkeeping (begin_run)
loader.py         Bundle: load a directory by file name or uploads by embedded schema id
common.py         palette, charts (Altair), tables, transcript widgets, badges, require()
app_pages/
  setup.py        Pipeline setup — project, target, discovery preview, config form, YAML editor, run buttons
  run.py          Run & review — job status (polled), review loop, results hand-off
  summary.py …    report pages: agent, intents, dataset, coverage, results, stability,
  stages.py       simulation, analysis, summary, stages & problems
```

## The project (`project.py`)

One choice drives the whole app: `st.session_state["project"]` is `None`,
`{"mode": "dir", "dir": <output folder>}` or `{"mode": "uploads", "bundle": Bundle}`.
Only the *Pipeline setup* page changes it (plus the `--dir` / `EVALBUILDER_UI_DIR` /
`?dir=` start-up argument, opened once); the sidebar shows it and offers *Clear
project*; *Run & review* and every report page derive what they show from it.
Without a project every page is empty and links back to the setup page; a folder that
has not run yet shows "No artifacts yet in `<dir>`".

`begin_run()` is the per-run bookkeeping the entry point performs before any page
renders: open the start-up folder once (or adopt a project injected from outside, as
the tests do), capture the setup widgets back into the persistent form, reload the
config if its file changed on disk, derive the project from the form (`sync`), and
load the bundle into `st.session_state["bundle"]`.

**Folder mode: the project is the setup form's output directory.** Picking a target
proposes `eval/pipeline/<name>`; typing another directory moves the project; opening an
existing folder (`open_dir`) loads its config into the form — `setup.project_config`
resolves it through the last `work/job.json`, then `report.json` (`config_path`, falling
back to the config embedded in the report), then a sibling `<dir>.yaml` — and records
the file's mtime; saving/running follows what the YAML says. Uploads are a read-only
project: the bundle is kept in the project itself (the uploader widget, like every
widget, forgets its files on navigation).

## Loading artifacts (`loader.py`)

`load_dir(path)` walks `layout.artifact_index` (root kinds by file name incl. legacy
names, per-run kinds under `results/`), unwraps dict-shaped artifacts, and returns a
`Bundle` (one attribute per kind, `None` when absent — `bundle.deployment` for
`deployment.json`; `problems` for unreadable files). `Bundle.run_ids` orders the runs
as the `infer` stage recorded them (falling back to `run`, the stage's name before
2026-09) and sorts the rest. `load_files(uploads)` identifies each uploaded JSON/YAML by its embedded
`schema` id, then by file name. `discover_dirs` scans `eval/pipeline/*` and
`docs/examples/*` for directories holding any known artifact. `project.bundle()` wraps
the cached loader (keyed by a fingerprint of paths + mtimes, so a running job's new
files show up) and returns an empty bundle for a folder without artifacts.

**Why by schema id:** a user can drop any subset of artifacts (even from an older
naming) and the app still knows what each file is; pages that need a missing
artifact say which file and which stage writes it instead of failing.

## Pipeline setup (`app_pages/setup.py`)

The page is the app's default (root URL) and **keeps its state while other pages are
visited** — see *Persistence* below.

1. **Project** — a selectbox over `setup.discover_projects()` (output folders under
   `eval/pipeline/*` and `docs/examples/*`, plus `eval/pipeline/*.yaml` configs that
   have not run yet, labelled *not run yet*), *new project…*, an *…or any output
   folder* path with *Open*, a status line (job badge, name, folder, config) and an
   expander to **upload artifacts instead** (read-only).
2. **Target agent** — a selectbox over `setup.discover_targets()` (placeholder until
   chosen) or a custom source/module/factory. *Discover structure* calls
   `setup.preview_target` (no LLM) and shows metrics (nodes, tools, pydantic models,
   schema edge cases), the node list (AST and live), a tools table (schema source,
   models, output schema, side-effecting, edge cases, used by) and per-tool expanders
   with `args_schema`, `output_schema` and the derived edge cases.
3. **Config** — widgets bound to `setup_*` keys: name, config path, models (agent /
   judge / generator / mock, default `claude-cli:claude-sonnet-5`), constraints (one per
   line), **general rules & instructions** (free text), coverage numbers incl. edge
   cases per tool, evaluators, mock miss policy, thresholds, repeats, simulate; a
   **Deployment** block — `setup_deploy_target` (local / docker / kubernetes /
   openshift), `setup_image_name`, `setup_image_registry`, `setup_namespace`,
   `setup_expose`, `setup_keep` — and a **Parallelism** block — `setup_infer_workers`,
   `setup_infer_backend` (threads / processes), `setup_eval_workers`; then auto-approve
   + approver and the output directory (= the project folder). *Generate YAML* →
   `setup.build_config(form).to_yaml()` into the editor (and the project follows the
   config's output directory); `setup.default_form` / `form_from_config` / `build_config`
   round-trip the deployment and parallelism fields into `deploy`, `inference` and
   `evaluation`. *Validate* reports the deployment checks too — a `claude-cli` agent
   model under a container target is refused there, not at run time.
4. **Config YAML** — an editable text area; *Validate* runs `setup.validate_text`
   (schema errors, then `problems()`); *Save config* writes the text to the config
   path; *Generate dataset & mocks only* / *Run full pipeline* save, start a job
   (`jobs.start_job`, mode `dataset` or `full`) and switch to *Run & review*. After
   any of them the form's name/output directory/target follow the YAML.

Design points: the form only mirrors a subset of the config — the YAML editor is the
full surface, and what is saved is the editor text, so anything the form does not
expose (per-metric thresholds, evaluator options, `stages.skip`, LangSmith) is still
editable. Every button acts through an `on_click` callback (callbacks run before the
next run's widgets exist, the only moment Streamlit lets code rewrite widget values),
and messages are stored in session state and rendered afterwards.

### Persistence

Streamlit drops the value of a keyed widget as soon as a run does not render it, so a
form spread over widgets forgets everything on navigation. The setup page therefore
keeps its truth in a plain dict, `st.session_state["setup_form"]` (form fields +
`target`, `yaml`, `config_mtime`): `seed_widgets()` gives every missing `setup_<field>`
key its form value before the widgets are created, and `capture_widgets()` copies the
widgets back at the start of every run (before Streamlit's cleanup) and at the end of
the page. Non-form state (the discovery preview, notices) lives in ordinary keys.
`refresh_from_disk()` compares the config file's mtime with the one recorded when it
was opened or saved: a change made by *Run & review* (feedback, approval) or by a job
reloads the form and YAML with a notice instead of being silently overwritten by the
next *Save config*.

## Run & review (`app_pages/run.py`)

The page follows the project (no selector of its own): a caption shows name, folder
and config; no project / uploads / a folder that has not run → an explanation and a
link to the setup page.

- **Job status** — a `st.fragment(run_every="2s")` while the job is running
  (`jobs.job_status`): badge (running / finished / stopped / lost), mode, start time,
  exit code, running or interrupted stage, `stopped after`; a **Stop job** button
  (`jobs.stop_job` SIGTERMs the job's process group and finalises work/job.json with
  `stopped: true`); the shared `common.job_progress` widget — a stage-level progress
  bar (every stage is pre-registered in work/state.json, the executing one is saved as
  `running`) plus, while the infer stage executes (`common._run_stage_active` accepts
  `infer` and the pre-rename `run`), a case-level bar and per-intent tallies from
  `work/run-progress.json`; a **Partial results** table of the cases completed in the
  current repeat; the stage table (status, seconds, attempts, reason/error — deploy,
  infer, simulate and teardown among them); the log tail. The sidebar shows the same
  widget compactly (badge + bars) in its own live fragment. When the fragment sees the
  job finish it triggers a full `st.rerun(scope="app")` so the sections below appear.
- **Review & iterate** (shown when `dataset` succeeded and `infer` — or `run` in an
  older directory — has not): case counts
  by review status, failure modes, the schema-edge cases table (tool, edge kind, field,
  input, injected mock override), mocked tools; a **comment / new instruction** text
  area with *Regenerate from* (`map | mocks | dataset`) → *Save feedback*
  (`setup.add_feedback` appends to the config) or *Save feedback & regenerate*
  (`jobs.start_job(mode="regenerate", from_stage=…)`). The config file is the one the
  job recorded, else the project's.
- **Proceed with evaluation** — approver name (required), an optional multiselect of
  cases to reject (`setup.reject_cases` → `review.status=rejected` with a note), then
  `setup.approve_in_config` and `jobs.start_job(mode="resume")`.
- **Deployment** (`_deployment_section`, when `deployment.json` exists) — the record
  (status badge, target, image, endpoint, expose, updated at; the served module, tools
  and model specs from the health facts; the error of a failed deployment) and, while it
  is `up` and no job is running, a **Tear down** button (key `run_teardown`, `deploy_down`)
  next to a **Check status** button (key `run_check_status`) that probes `deploy_status`
  once and keeps the result (healthy / unhealthy, ready replicas, checked-at) in
  `st.session_state["run_deploy_status"]`, because that probe shells out and waits on the
  network and so must not run on every rerender; a caption points at the record and at
  `work/deploy/` (rendered files, command log).
- **Results** (when `report.json` exists) — verdict badge, overall score, counts,
  verdict reasons, and *Open results in the report pages*, which switches to the
  Summary page (the project is already the folder).

**Why this shape.** The review loop is exactly the CLI loop (`--until dataset` →
feedback → `--resume --from … --until dataset` → `--resume`) expressed as buttons;
the page never edits artifacts itself except through the same helpers the CLI uses
(`set_review`, config save). Polling files rather than holding a process handle keeps
the page correct after reloads and lets several browser tabs watch one job.

## Report pages

Each page is a `render()` that reads the bundle, calls `require(bundle, kinds…)` (no
project → "choose one on Pipeline setup" with a page link; no artifacts yet → the
folder name; a missing kind → a warning naming the file and stage), and renders with
stable anchors (`st.header(..., anchor=…)`, `st.subheader(..., anchor=…)`) and widget
`key`s so the browser tests can address them:

| page | anchor | shows |
|---|---|---|
| Agent graph & tools | `agent` | Graphviz graph (AST edges or live edges; tool links), merged nodes with prompts and evidence, conditional edges, tools table (schema source, models, output schema, side-effecting, edge cases), per-tool expanders with args/output schemas and edge cases, constraints, topics |
| Intents & scenarios | `intents` | intents with evidence and case counts, scenarios per intent, failure scenarios, applicable failure types with gating evidence |
| Dataset & mocks | `dataset` | filterable case table (status, intent, failure mode, variant, edge kind), case detail (inputs, follow-ups, references, edge badge, per-case mocks, review note, LangSmith id), review counts, tool fixtures |
| Coverage | `coverage` | planned vs covered by kind, plan cells, gaps |
| Eval results | `results` | aggregate metrics vs thresholds, per-run metrics, slice heatmaps, per-case score matrix, failing cases with judge comments, case drill-down with transcript and tool calls per run |
| Stability | `stability` | unstable cases / outputs / evaluators, suspect judge comments, per-case trajectory/output hashes |
| Simulation | `simulation` | scenario outcomes, transcripts, violations |
| Analysis | `analysis` | summary, verdict explanation, failure patterns, weak slices, recommendations, evaluator issues |
| Summary | `summary` | verdict + reasons, a "deployed to `<target>` at `<endpoint>`" caption (from the report's `deployment` summary or the record), headline metrics (overall score, metrics passing, cases, coverage, stability), metric pass-rate chart with threshold ticks, stage timeline, coverage summary, stability summary, mocking summary, analysis summary, problems — last in the *Evaluation* group, after Analysis |
| Stages & problems | `stages` | timeline, per-stage details and artifacts (deploy / infer / teardown included), problems, generator calls, artifacts loaded (`deployment.json` among the kinds), config |

Navigation: *Pipeline* (Pipeline setup — default, Run & review), *Agent*, *Data*,
*Evaluation* (Eval results, Stability, Simulation, Analysis, Summary), *Run* (Stages
& problems). Streamlit serves the default page at the root URL only, so the setup
page has no `/setup` URL.

Charts follow one small palette (`common.py`: categorical blue/orange/aqua, status
colours, a sequential blue ramp) and use `alt.Step` heights because layered Altair
charts ignore fixed heights under Streamlit.

## Testing the UI

- **Headless** (`tests/test_ui_pages.py`, `tests/test_ui_pipeline_pages.py`): every
  page is rendered with `streamlit.testing.v1.AppTest` the way the app renders it
  (`project.begin_run()` then `render()`), against the committed example directories
  as folder projects, without a project, for a folder that has not run, for a partial
  upload (each page must explain what is missing) and as an uploaded read-only
  project. The setup/run suite renders whichever page `session_state["page"]` names,
  so switching it between runs is exactly what sidebar navigation does to session
  state: it covers project selection (target → folder everywhere, opening an existing
  folder loads config + results, *Open* on any path, *new project…*), the sidebar's
  *Clear project* callback emptying every page, the form/preview/YAML surviving
  navigation, the YAML's output directory moving the project, config reload after a
  change on disk, the run page's review section on a stopped-after-dataset folder, the
  deployment and parallelism form fields reaching the YAML (and *Validate* refusing a
  claude-cli agent model under a container target), and the run page's Deployment
  block: an `up` record with a dead process shows *unhealthy* only after **Check status**
  and **Tear down** marks it `down`; a `failed` record shows its error and no button.
- **Browser** (`tests/ui/test_playwright.py`, `tests/ui/test_playwright_flows.py`;
  marker `ui`, skipped without chromium): a session fixture starts the app on a free
  port with `EVALBUILDER_UI_DIR`; the report suite checks the landing page (setup with
  the start-up folder as project, Summary after Analysis in the sidebar), walks every
  report page of the support-bot example, and drives uploads → read-only project →
  *Clear project*; the flow suite runs the interactive flows end to end with offline
  models (`scripted:` agents and the examples' offline generators) and asserts on the
  artifacts written to disk: setup state across pages + clear, opening an existing
  project, setup → discover → generate/validate/save YAML; dataset-only run → review
  → feedback → regenerate → approve (with a rejection) → evaluate → results → report
  pages; a full autonomous run; the pydantic-schema agent flow (edge kinds incl. the
  injected malformed output); the smallest agent (weather_bot, 4-case dataset)
  through review, evaluation — the Deployment block on Run & review after the local
  target was torn down, the deployment caption on Summary — and every report page; and
  the setup form's *Deployment target* / *Inference workers* fields landing in the YAML.
- **Pipeline end to end on small agents** (`tests/test_e2e_small_agents.py`):
  weather_bot with a 4-case dataset through `run_pipeline` (full run), the review loop
  (`--until dataset` → feedback → regenerate → reject/approve → resume) and the UI's
  job modes as real subprocesses (marker `slow`).

Streamlit-specific gotchas the tests encode: select widgets are react-aria comboboxes
(`[role='option']`, multiselect needs a forced click, its first option is "Select all",
its menu stays open), `st.dataframe` renders on a canvas (assert via markdown/code),
the status widget can appear late after a click, a job's completion is trusted from
`work/job.json` on disk before the page text, the default page is served at `/` only, and
keyed widget values vanish when the widget is not rendered (hence the persistent form).

## Limitations

- Single-user, local: no authentication, no multi-user coordination beyond the
  refusal to start a second job on a running directory.
- One project per browser tab; the setup form survives navigation but not a server
  restart. Unsaved YAML edits are dropped when the config file changes on disk.
- The form covers the common config keys; advanced options (`deploy.build`, `deploy.env`,
  `image.push`, `inference.timeout`, per-metric thresholds, …) are edited in the YAML.
- The Deployment block acts on the recorded deployment only (`deploy_status`,
  `deploy_down`); starting one without a pipeline job is a CLI matter
  (`evalbuilder deploy up`).
- The job log is tailed from a file (last 60 lines); very verbose generator output
  is truncated on screen (the file is complete).
- Uploaded-files mode is read-only (no jobs) because there is no directory to run in.
- Large datasets/runs render as full tables; there is no pagination.


## Skills and the LLM mock layer in the UI (2026-09-01)

- **Pipeline setup**: the structure preview shows a *Skills* metric, a tools table
  with `kind` / `mocked` columns and an *Agent skills* table; the config form has a
  *Mock model* input, the miss policy gains `llm`, plus *On invalid mock* and
  *Generate strategies* (`setup.default_form` / `form_from_config` / `build_config`
  round-trip the new fields).
- **Run & review**: the dataset summary line names the policy, the mock model and the
  strategies with the number of cases selecting each (`setup.dataset_summary`).
- **Agent graph & tools**: a *Skills* metric and section (description, instructions,
  references, used-by, allowed tools); node expanders list the skills they embed or
  load and the disclosure style; the tools table shows `kind`.
- **Intents & scenarios**: scenario expanders show the skills they exercise.
- **Dataset & mocks**: the header names the policy, mock model and default strategy;
  the case table gets a `strategy` column, the case detail shows the selected strategy;
  a *Mock strategies* section renders the world and one tab per strategy (behaviour,
  examples, fallback per tool) from `mock-strategies.json` or the dataset's embedded copy.
- **Coverage**: a *Skills* table (cases per skill, uncovered skills warned).
- **Eval results**: the case drill-down shows the LLM-mocked call count and a *Mock
  calls* table per run (layer, strategy, rule index, validation, repairs, fallback).
- **Summary**: a *Mocking* section (layers, policy, model, strategies, calls per layer,
  a warning when unstable cases had LLM-mocked answers); the sidebar counts skills.
- Tests: `tests/test_ui_pages.py` renders every page over an offline support_bot run
  with on-demand skills and `on_miss: llm` (module-scoped fixture);
  `tests/test_ui_pipeline_pages.py` drives the new form fields into the YAML and back;
  `tests/ui/test_playwright_flows.py::test_skills_and_llm_mock_layer_end_to_end` runs
  the whole flow in a browser.
